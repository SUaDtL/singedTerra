# WB-02 — Shield-first versus fire-first

Document revision: 1. Source baseline: `e195f81bd344c0ae75d1fc4a8b224401f2d5007f`.
Delivery: PR #520, `codex/classic-weapon-balance-slice`. This is development-only
measurement work. It does not change live shields, weapons, prices, AI, rewards
or campaign code. The commander-identity fix remains in the preceding commit.

## Question

**When is spending a turn on protection preferable to taking a shot?**

WB-01 measured an individual held weapon's complete effects. It did not model
purchases or an opponent's response. This slice examines one interaction:
normal/heavy shield preparation versus firing immediately, over the same maximum
two commitments per seat. It reuses WB-01's actual-weapon aiming search and the
ordinary `GameEngine.applyAction` path. P13 remains the full-match pacing owner.
There is no new physics, live CPU implementation or general combat framework.

## Run

```bash
npm run check:weapon-balance
npm run balance:shield-exchange -- --out=/tmp/wb02.json
npm run balance:shield-exchange -- --scenario=open-42 --weapon=heavy_missile --out=/tmp/wb02-heavy.json
```

`balance:weapons` still defaults to WB-01. Its new optional
`--study=shield-exchange` flag selects WB-02; invalid studies, scenario/weapon IDs
and repeated options fail. Existing output files are never overwritten. The
full study is opt-in; the small inline exchange check joins the ordinary root
check through `check:weapon-balance`. No new dependencies or runtime imports.

## Experimental design

The complete study contains **108 exchanges**:

| Axis | Values |
|---|---|
| Terrain/boundary | `open-42`, `open-7`, `wrap-13` from the existing WB-01 constructors |
| Offensive tool | Missile, Heavy Missile, Sandhog |
| Subject strategy | Fire twice; normal shield then fire; heavy shield then fire |
| Subject seat | P1 or P2; P1 remains the real first actor in every case |
| Starting inventory | Untouched stock; or disclosed depleted-stock / 30,000-credit checkpoint |

Stock means the real opening ammunition and 8,000 credits. Depleted-30k is
**synthetic**: clear finite ammunition and set both seats to 30,000 credits,
leaving health, terrain, positions and the unlimited basic shell unchanged. It
is a controlled restocking question, not a claim that a natural match reaches
that state. Both configurations and complete start/end inventories are recorded.

The subject either fires immediately or uses one shield on its first available
turn. Its opponent fires the same requested offensive weapon on both turns.
Both aim greedily from the changed terrain/wind using WB-01. This opponent is an
**experimental policy**, not the shipped CPU and not a human-player model.
There is no movement, shield refresh, equipment optimization or look-ahead win
search. Choosing a shield changes future terrain and therefore later aims.

A missing item triggers one ordinary bundle purchase, not an ammunition grant.
A rejected shield purchase falls back to offense and the strategy is explicitly
marked unexecuted. A rejected offensive restock falls back to the unlimited
basic shell. Price and arms-level admission come from the actual engine. The
runner does not pretend a player can pay one-third of a bundle at checkout.

The window stops at two commitments per seat or the actual terminal state,
whichever occurs first. Dead seats never get forced replies. Reaching the
horizon with survivors is **not a draw**, and results are not aggregated into
match win rates. Unresolved/blocked windows have no summary and cannot produce
comparative advantage claims. A shield never executed is identified separately.

## Evidence produced

For each case the JSON records actual purchases (including rejection and stock
grant), cash spent, earned credits, ending cash, remaining inventory, consumed
replacement value, turns, actual shots, shield uses, hull/shield state, physical
per-action changes, score credit, fallbacks, simulation ticks and search work.
Consumed replacement value is an amortized catalog reference, **not a cash debit
or a claim that unused stock is liquid money**. It is not added to cash to create
an invented utility score. Paired deltas keep hull, opponent hull, cash and shots
separate. Pairing is owned by the runner's unchanged fixture; the comparison
helper checks recorded inputs, not cryptographic or replay identity.

WB-01 searches both firing directions over its 114-point grid, uses the existing
missile search only for coordinate proposals, and refines two candidates. Each
actual-engine probe has a 2,048-tick ceiling. Counts include sensitivity and
best-aim rechecks; missile-proxy probes are separately counted. Equal budgets do
not prove global optimality. No aiming-error distribution is modeled here.

See [the baseline table](wb02-baseline.tsv) and [execution receipt](wb02-receipt.json).
The full JSON is generated by the commands above. All values in the table are
measurements, not future balances or CI golden expectations.

## What the measured cases establish

**Protection has a real turn cost.** In a controlled fixed-aim miss witness,
fire-first gives the subject two shots and 1,000 earned credits; shield-first
allows one shot and 500 earned credits. The opponent takes both replies in
either case. This is pinned in the fast check to catch fake zero-cost shielding.
The witness deliberately misses; it does not measure typical tactical benefit.

**Stock availability and replenishment are different balance questions.** A
free opening heavy shield and a 30,000-credit heavy-shield purchase cannot be
priced as the same decision. In the depleted-30k fixed-aim witness, the subject
spends all 30,000 on two Heavy Shields, consumes one, and has to fire the free
basic shell next because it cannot buy a Heavy Missile bundle. Normal Shield
costs 20,000 for three, leaving enough to buy the 6,000-credit Heavy Missile
bundle. Unused charges and missiles remain visible in the ending inventory.

**More shield capacity is not a universal response to terrain attacks.** In
`open-42 / stock / Sandhog / subject P1`, normal- and heavy-shield-first both
finish the window with 45 hull, while fire-first retains 100 hull. The shields
retain different reserves (approximately 61.98 and 181.98). This is a result of
the actual exchange, not a formula deriving fall damage from displacement.

**The stronger shield does matter under some direct pressure.** In
`open-7 / stock / Heavy Missile / subject P1`, normal-shield-first reaches an
actual terminal loss while heavy-shield-first retains 75 hull at the horizon.
That survivor is not recorded as a match win. In contrast, `open-42 / stock /
Heavy Missile / subject P1` can finish the opponent with its first fire-first
shot; shielding gives up that immediate finish in this search policy.

These are counterexamples to blanket statements such as “always shield first,”
“heavy shield is pointless,” or “halve shields to shorten every match.” They are
not a representative sample of player skill, all weapons, all terrain or the
whole economy. Observations under a greedy short-window policy do not establish
optimal player behavior or enjoyable match length.

## Targeted direction from this slice

Separate **opening access**, **activation opportunity cost**, and **restock
price** before choosing a numerical change. A worthwhile next candidate is the
free starting Heavy Shield versus its full-price replenishment role. Preserve
normal/heavy distinctiveness and terrain counters while testing any candidate.
Do not simultaneously change both capacities, both prices, fall damage and
starter ammunition: that would obscure which change helped.

This PR does not approve a removal, new capacity or new price. An actual live
change must define its classic execution contexts and historical replay/ST1
compatibility first. Do not infer permission to regenerate retained challenge
artifacts or change account rewards. Ash Road remains outside dedicated work.

## Verification and limits

Inline checks exercise equal turn budgets, actual opponent replies, bundle
purchases, retained stock, rejected purchases, basic-shell fallback, legal use
of owned shields despite a restricted store, P2 initiative, real early terminal
state, unresolved search/settlement, blocked actors, source/catalog isolation,
repeatability and comparison-input refusal. They use ordinary action paths;
the few precondition changes are labeled in the check itself.

Local execution uses Node 22.16.0 with a temporary TypeScript 5.8.3 loader outside
the repository; this is **not** the pinned Node 24/tsx toolchain. The new full
study repeats identically under that environment. The e195f81 parent has now
passed hosted canonical CI, including root checks, database, client tests,
build, Edge and browser jobs (run 35942712184). That receipt validates the parent,
not this new slice. New-head validation is reported on PR #520 after publication.
No browser game playtest, physical-device test, merge or deployment is claimed.

WB-01 and P13 historical artifacts remain byte-for-byte unchanged. New balance
source files naturally change the CLI's whole-input fingerprint; that is not a
reason to rewrite an older receipt. The existing P13 retained-artifact mismatch
was disclosed in WB-01 and was not suppressed in this slice. The ST1 manifest
changes only its package-script binding and reviewed disposition.
