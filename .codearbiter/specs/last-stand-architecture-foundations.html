Last Stand: extensible game and release foundation

Restructure Last Stand into a coherent product architecture, including shared UI, content authoring, platform services and repeatable browser/Android development builds. Sweeping implementation and presentation changes are allowed when they make the game easier to extend and release; protect player progress and explicit product commitments.

SEC-SMARTS

SMARTS design rationale

Blocks

Decision: organize Last Stand primarily around feature modules with shared helpers, or establish explicit domain/application/content/platform layers within Unity. Both can reuse current assets and rules. Owner prioritizes long-term extensibility and release readiness over minimal diff size.

References: SRC-RELEASE-OWNER SRC-PLATFORM SRC-CONTENT
LensFeature-first evolutionModular product architecture
ScalableAdequate. Features can grow, but content and platform changes cross feature owners.Strong. Content definitions and platform adapters extend without duplicating feature implementations.
MaintainableAdequate. Smaller migrations preserve familiarity but leave more cross-feature coordination.Strong. Explicit ownership and composition make future changes and replacement responsibilities discoverable.
AvailableIndifferent. Both retain local play and the same deployment targets.Indifferent. Both retain local play and the same deployment targets.
ReliableStrong. Smaller transitions reduce immediate regression exposure.Adequate. Larger migrations require durable-state fixtures, fault injection and playable checkpoints.
TestableAdequate. Feature checks remain useful but platform assumptions still need careful isolation.Strong. Pure rules, adapter contracts and independent migration fixtures provide direct tests.
SecurableIndifferent. Both retain local trust boundaries and require vetted dependencies.Indifferent. Both retain local trust boundaries and require vetted dependencies.
References: SRC-PLATFORM SRC-CONTENT SRC-LOOP

Recommend the modular product architecture. Scalable, Maintainable and Testable drive the choice; larger migration risk is managed with independent save/economy fixtures and usable vertical slices. No engine replacement or generic framework is selected.

References: SRC-RELEASE-OWNER

Unknown execution evidence: actual Android toolchain/device availability and target frame/memory budgets. missing_observation=preflight and profiling; decision_critical=false for ownership design, required before target build/performance acceptance. Never count an unavailable target as qualified.

References: SRC-PLATFORM

Broad class, file, assembly, content and UI changes are allowed. Preserve progress, retained run editions and required capabilities. Non-SMARTS cost is a larger sprint and migration workload; delivery slices remain reviewable and runnable.

Foundation delivery and remaining release work

Blocks

This sprint produces a usable game foundation and browser/Android development candidates. It is broader than refactoring, but does not assert that completing architecture alone makes a commercial release ready. Preserve the roadmap: the browser is the current proof surface and Android the first native target.

References: SRC-RELEASE-OWNER SRC-PLATFORM

  • Account, cloud-save, purchases and store distribution are product decisions if required, not placeholder features to invent. Publication, signing-account access and commercial spending remain separate.
