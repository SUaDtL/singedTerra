## Problem

The Commander Career presentation exists but correctly refuses to claim rank from forgeable casual XP. The hosted shared-engine replay probe has now passed authenticated production execution, yet a player still has no real match path that produces verified progression, no honest promotion moment, and no concrete reason to choose a career deployment over another casual duel.

The affected player is a signed-in commander. Done means that player can deliberately launch one bounded, server-owned Verified Deployment against a CPU opponent, complete the match locally, have the server independently replay only its committed canonical actions, receive one idempotent verified-XP award, and immediately see the earned rank or next rank milestone. Ordinary hot-seat remains casual and unchanged.

## Approach

Implement the accepted ADR-0014 lifecycle as one deliberately constrained Verified Duel: an authenticated start endpoint returns one resumable owner-private session with immutable server-owned deterministic config; the browser runs that exact contract through the existing shared engine while persisting only accepted human fire commitments; the verifier regenerates every CPU turn from one shared deterministic duel policy, enforces a fixed salvo cap, and deterministically adjudicates any surviving tanks at the cap. An authenticated completion endpoint replays that complete contract and atomically consumes the session into one immutable verified result with its private canonical evidence. `account_summary` exposes casual history and verified progression as separate authorities, and the existing Commander Career model consumes only the verified branch.

This is preferred over awarding the fixed hosted probe or trusting a client outcome. The strongest counter-consideration is scope: it adds an additive migration, three Auth-owned functions, a bounded transport mode, a shared duel controller, recovery, and player-facing integration. That cost is required to produce a real, honest career outcome instead of another non-awarding proof.

## Scope

- Add owner-private, additive `verified_deployments` and `verified_match_results` storage, an INTERNAL service-only `verified_deployment_contracts` start-control row, plus service-role-only transactional start/abandon/complete RPCs.
- Add strict account-authenticated start, abandon, and completion Edge Functions with a coarse pre-Auth per-IP limiter plus a fail-closed Auth-derived per-account limiter, exact request/response contracts, generic failures, and no secret or raw-error logging.
- Add a bounded-JSON wrapper that applies the coarse limiter, authenticates, applies the strict account limiter, and only then counts streamed UTF-8 bytes under read/cancel deadlines before parsing. `Content-Length` is an early rejection only, never the authority.
- Add one shared `verifiedDuel` contract used by browser and verifier: fixed seed/config pool, Baby Missile only, aim/power plus fire only, six human salvos, deterministic server-regenerated CPU salvos, and deterministic cap adjudication. Every allowed path must satisfy the shared tick ceiling, and the adversarial full-duel corpus must remain below both the measured replay target and the current hosted 200 ms active-CPU limit.
- Make engine action acceptance explicit: the shared action-application seam returns whether an action committed, and only an accepted human fire is folded into the transcript. Aim-only and rejected actions never enter it.
- Persist the versioned active descriptor and human transcript after each commitment. Refresh reconstructs the duel from server config plus transcript; account changes freeze completion until the original owner returns; terminal transport failure remains visibly retryable only while the server expiry remains open.
- Complete once at terminal state, retry safely, refresh the trusted account summary, and render verified XP, rank, promotion, or explicit verification failure in the already-open After Action Report.
- Add a signed-in-only “Verified deployment” action to the Local Battery route with concise connectivity, expiry, fixed-rules, and salvo-cap disclosure. Casual deployment remains the primary always-available action.
- Extend the existing no-body `verified_replay_probe` and exact diagnostics validator with one immutable maximum-probe/full-duel workload. It remains non-awarding, side-effect bounded, and compile-time allowlisted; do not create a generic request runner or repeatedly mint career XP from diagnostics.
- Deploy the additive migration/config/functions after exact-head review and CI, then verify production start, completion/idempotency, summary, rank, and ordinary casual behavior through the browser-managed session.

## Out of scope

- No gameplay advantage, weapon/tank/world lock, scarce reward, entitlement, leaderboard, matchmaking rating, or anti-human/anti-bot claim.
- No verified online-room progression, arbitrary player-selected verified config, live per-action server writes, general server-authoritative turns, or duplicate physics implementation. The server generates CPU commitments only inside the bounded post-match verifier.
- No change to casual hot-seat XP arithmetic or ADR-0012’s trust ceiling.
- No Google SSO, password recovery, email delivery, dependency, crypto, service-key handling, or destructive migration.
- No tactical-objective system in this slice. That remains the initiative’s next player-retention milestone after verified rank is production-real.

## Decided parameters

- V1 evidence marker remains `verified_replay_v1`; verified progression version remains `1` with 100 XP for completion plus 100 XP for a win.
- A session expires 30 minutes after creation. Repeated start calls return the same unexpired active session and exact config. Only an explicit exact-shape abandon call may replace it before expiry. The HUD always shows the remaining verified window, warns at five minutes and one minute, and stops accepting verified inputs at expiry. Expiry honestly ends rank eligibility: the player may explicitly continue the local duel as casual or return to the battery, but cannot retry or claim a verified result.
- Session identity is a server-generated UUID. The client never supplies user id, seed, config, winner, XP, level, rank, reward, or totals.
- The completion body is exactly `{ sessionId, transcript }`; it contains accepted human fire commitments only and is capped at 1,024 UTF-8 bytes before parsing. Start accepts no body. Abandon accepts exact `{ sessionId }` under a 128-byte limit. Bounded reads use a 2-second body deadline and a separately bounded 250 ms cancellation attempt; `Content-Length` is only an early rejection.
- V1 Verified Duel uses the exact server-owned seed allowlist `[17, 42, 73, 109]` and fixed options: two seats, Commander versus a bounded deterministic CPU, `maxWind: 6`, `gravity: 0.15`, open walls, no hazards, one round, zero interest, sudden death off, arms level 0, decisive starter-weapon falloff, and no teams. The server stores the selected seed; the client cannot request one.
- V1 preserves the native integer aim controls: human angle `0..180` and power `0..100`, with Baby Missile as the only weapon. Its canonical transcript is at most six exact `{ angle, power }` human-fire commitments. Each settled human shot is followed, unless already terminal, by one shared two-pass bounded CPU search with Baby Missile forced: right-facing coarse angles `[5,20,35,50,65,80,90]` or mirrored-left `[90,105,120,135,150,165,175]`, crossed with powers `[20,40,60,80,100]`, then angle offsets `[-6,-3,0,3,6]` crossed with power offsets `[-8,-4,0,4,8]` around the best coarse candidate. Clamping and deduplication permit no more than 60 unique probes. CPU actions are regenerated and never accepted from the transcript.
- The duel ends on an ordinary engine terminal result or immediately after the sixth generated CPU salvo settles. Cap adjudication is external to the ordinary engine state machine and compares alive status, then health, then `totalDamage`, then draw; the controller freezes further input and supplies the same terminal outcome to browser and verifier without forging a generic `GameState` win.
- The engine bounds one Baby Missile flight at 240 ticks and animated settle at `ceil(600 / 4) + 1` ticks, yielding 391 live ticks per salvo and 4,692 live ticks per 12-salvo duel. CPU planning adds at most `60 × 240 × 6 = 86,400` simulated physics ticks. Under fixed V1 launch/wind/gravity/drag constants, displacement is below 24 pixels per tick, so one-pixel swept collision adds at most `60 × 240 × 24 × 6 = 2,073,600` collision samples. The executable oracle imports and proves those constants, exhausts every allowed seed/angle/power single-salvo tuple, exercises maximum-probe CPU states and six-turn workloads, and runs an adversarial multi-salvo corpus. The complete workload must stay under a conservative 100 ms local target and pass the hosted non-awarding production probe beneath the current 200 ms active-CPU limit.
- A legal unexpired V1 duel always reaches an awardable terminal result inside that measured envelope. Ownership, version, malformed-body, and transport failures remain explicit retry/abandon states without a rank claim while unexpired. Expiry is not called recoverable: it ends verified eligibility, freezes the verified controller, and offers explicit casual continuation without converting the gameplay outcome into a server failure or rank claim.
- Authenticated endpoints retain the existing coarse IP shield but additionally call the DB limiter with an Auth-derived account bucket before body consumption or replay. Account-limit storage failure is fail-closed. Completed-session retry compares the bounded stored transcript and returns the immutable receipt without replay; conflicting evidence is rejected.
- Completion is idempotent by session id. Concurrent or repeated completion returns the same immutable result and never awards twice.
- Verified tables are owner-private and excluded from Realtime. Authenticated clients receive no direct write privilege; all writes use exact service-role RPC grants.
- The bounded canonical human transcript is stored as owner-private immutable JSONB with the verified result so the award can be reproduced and conflicting completions can be rejected. It contains no credential, email, display name, user id supplied by the client, or raw browser state.
- Engine/ruleset numbers are not treated as executable version selection. A service-only contract-control row starts disabled and records `starts_enabled`, authoritative `disabled_at`, and `last_started_at`; it gates only creation of new sessions, so start retry still resumes an existing unexpired session while disabled. A checked-in drain command disables starts, reports `safe_after = COALESCE(last_started_at + 30 minutes, disabled_at)`, and refuses rollout until that time has passed and zero unexpired sessions remain. Old completion/abandon stay deployed during the wait; replay backend deploys before the strict-version-refusing client; starts are re-enabled only after production verification. CI identifies governed replay-semantic paths and requires the contract-version/drain manifest, while the runtime command proves the production wait.
- Production diagnostics may validate read-only summary shape after a real player award, but must not create or complete awarding sessions automatically.

## Acceptance criteria

1. An authenticated start request with no body atomically creates or resumes exactly one unexpired deployment for the Auth-derived account and returns the identical V1 server-owned config, limits, UUID, and expiry on retries; only explicit abandon replaces it. Missing/malformed/rejected Auth, profile failure, or storage failure returns a generic response and creates no divergent session.
2. The additive migration enables RLS, grants no anonymous or authenticated table access or RPC execution, grants the service role only required operations, classifies every table/column, stores one immutable private canonical transcript/result per session, provides an INTERNAL service-only contract-control row whose disabled state permits resume but forbids new sessions, and proves concurrent start/abandon/complete idempotency without modifying prior migrations.
3. The shared action seam identifies real engine acceptance, and the recorder emits one canonical human fire only after an accepted commitment; rejected fire, aim/select, CPU, move, buy, shield, and round-transition inputs emit nothing. Browser replay plus verifier-generated CPU turns produce the same cap/terminal outcome.
4. A signed-in player can launch the fixed Verified Deployment from Local Battery without re-entering identity; anonymous, loading, unavailable, and authenticated-error states cannot launch it and instead preserve ordinary casual play.
5. The bounded-JSON request path applies coarse IP and fail-closed Auth-account limits before body consumption, then enforces the exact 1,024-byte completion / 128-byte abandon limits and 2-second read / 250 ms cancel deadlines, rejecting oversized, chunked-overflow, lying-`Content-Length`, invalid-Unicode, stalled-read, and stalled-cancel bodies before JSON parsing; completion accepts only exact `{ sessionId, transcript }`, derives identity/config from the owner session, and rejects expiry/ownership/version/shape/policy failures before mutation without trusting client outcome or totals. Same-account requests across multiple IPs share the account bucket; limiter failure refuses work.
6. The shared Verified Duel verifier regenerates CPU turns, enforces the fixed human action policy, exhausts all 73,124 allowed single-salvo seed/angle/power tuples, proves the 391/4,692 live-tick, 60-probe-per-CPU, 86,400 simulated-tick, and 2,073,600 swept-sample ceilings from shared constants, and reaches the same terminal/cap adjudication across maximum-probe and adversarial full-duel workloads inside the 100 ms local target and hosted non-awarding probe. Completion atomically stores exactly one private transcript/result; same-evidence retries return the immutable receipt without replay, conflicting evidence is rejected, and transaction failure leaves no partial award.
7. `account_summary` keeps existing casual totals unchanged and adds an exact `verifiedProgression` branch derived only from immutable verified results; malformed, truncated, duplicated, unowned, or failed reads fail closed without a rank claim.
8. The versioned local descriptor restores the exact server config and accepted human transcript after refresh, never transfers across accounts, and keeps terminal completion retryable only before expiry. The HUD exposes the expiry countdown and five/one-minute warnings; at expiry the verified controller stops accepting input and offers explicit casual continuation or battery return. The After Action Report distinguishes pending, verified loss/win XP, promotion, next-rank progress, expiry/policy refusal, and transport failure without turning casual XP into rank.
9. The verified path remains usable and contained at desktop, compact mouse, and touch layouts; launch/fixed-rules disclosure, salvo counter, pending/retry state, and result copy do not overlap or push the battlefield/HUD out of its layered frame.
10. Rate limits, function config, security controls, migration and drain verification, the no-body/no-award hosted maximum-probe/full-duel receipt, causal RED/GREEN tests, mutation checks, full local matrices, one adversarial exact-package review, exact-head hosted CI, ordered additive backend/client deploy, and authenticated production start/complete/idempotency/summary evidence all pass before merge completion is declared.

## Open questions

None. ADR-0014 resolves the trust architecture; the maintainer’s explicit approval resolves this bounded implementation route. Tactical objectives and broader replay ceilings remain later initiative decisions, not blockers for V1.

## Negative completeness check

If every criterion passed and nothing else changed, the previously broken outcome would be repaired: a signed-in player could earn the first honest Commander rank through a real match and understand whether the award succeeded. The larger retention initiative would still lack tactical objectives and long-term challenge history, which are explicitly out of scope and remain queued as the next milestone.

## Adversarial design challenge

The pre-implementation adversary blocked the first design because it could accept browser-authored CPU mistakes, invalidate a launched session on start retry, parse an unbounded body, and finish a legal local match outside unrelated fixture ceilings. The corrected design removes those failure classes: human-only commitments, server-regenerated CPU, resumable start, bounded streaming JSON, a fixed salvo cap with deterministic adjudication, persisted private evidence, refresh recovery, and deployment drain for replay-semantic version changes. The remaining cost is reduced V1 ruleset freedom; that is preferable to a career award that is sometimes unverifiable or dishonestly earned.
