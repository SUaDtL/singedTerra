SEC-RULES

Combat and checkpoint contracts

Blocks
  • Automatic combat remains the product: keep the main cannon, one auxiliary fitting and current pause/half-step speed controls.
  • New enemy composition is deterministic by saved rules edition, tier, wave and ordinal. Preserve the current finite 20-enemy group bound and model capacity; an elite replaces a slot.
  • Use one armor calculation with minimum positive damage for ordinary hits and an explicit penetration trait. No hidden UI-only damage formula. Mortar uses deterministic area membership/tie order and one hit per target per shot.
  • New enemy types may have authored value multipliers, but rewards pass through the existing fractional Scrap/yield/logistics ledger; repeatable Salvage and once-only milestones remain separate.
  • Checkpoint every cleared wave with HP, upgrades, resources and new mechanics state in the same profile transaction. Restart loses at most unfinished-wave progress and resumes paused. Research time remains real time.
  • Legacy active runs must keep their old enemy roster, timings, costs and rewards, not merely their old shop prices. New profile unlocks can appear after migration but cannot retrofit a different fitting into that active run.
References: SRC-ARCH SRC-COMBAT SRC-INTENT
SEC-MIGRATION

Progress preservation and milestone backfill

Blocks

Proposed policy: existing earned best-wave records qualify for the new armament/tier unlocks exactly once during migration, without paying historical Salvage again. Missing history earns no invented unlock. This avoids requiring a player who already cleared the target to repeat it, while retaining reward accounting. Keep this backfill and schema migration atomic and independently tested.

References: SRC-REWARDS

Persist explicit stable IDs/edition references with a bounded adapter for old ordinals. Unknown future versions or missing required old definitions must enter safe recovery without silently downgrading or rewriting the save.

SEC-SMARTS

SMARTS design rationale

Blocks

Material alternatives: extend the existing typed catalogs with focused domain mechanics; or introduce a generic external content/ability interpreter now. A release-qualification-only sprint is also a valid product priority and was considered; the owner approved the presented combat-depth scope.

LensFocused content extensionGeneric ability interpreter
ScalableStrong for the authored four tiers/five fittings; definitions feed existing consumers.Strong theoretical breadth, not yet justified by actual content.
MaintainableStrong: concrete owners and small mechanic strategies.Weak now: parallel schema/runtime and extra compatibility surface.
AvailableStrong: existing offline/local runtime, no service dependency.Adequate: local interpreter still adds loading/failure cases.
ReliableStrong: saved edition routing and existing transaction owner.Weak: wider execution/migration change before foundation acceptance.
TestableStrong: pure combat cases and independent replay fixtures.Adequate: requires both interpreter and every authored program verified.
SecurableStrong: bounded compiled mechanics and validated content.Weak relative: additional untrusted-content execution surface.
References: SRC-ARCH SRC-CONTENT SRC-CI

Decisive lenses are Maintainable, Reliable and Testable; select the focused extension. Unknown: exact coefficients and device frame/memory budgets, missing observation = production-model measurements and physical-device traces. These are not decision-critical to the extension method, but they are required before content/target acceptance.

Load-bearing assumptions: four playable tiers is a useful next increment; one auxiliary slot and the current local progression model remain. The owner approved this content list on 2026-10-28.

Non-SMARTS constraints: avoid stacking more unqualified implementation on red CI; no new paid tools or services; real device and endurance availability affects delivery timing. The owner explicitly values substantial sprints and a releasable game.

SEC-COMPLETE

What a successful sprint demonstrates

Blocks
  • Five fittings are visibly different, usable and worth choosing in measured matchups.
  • Four tiers use the same scalable preview selector and retain meaningful lower-tier farming.
  • Wave info explains actual new enemies and payouts; no stale hard-coded inventory.
  • Old and new runs survive update/restart without rewriting earned progress.
  • Current-source tests, builds and player journeys support their precise claims; unresolved physical-device or real-duration checks remain open rather than disguised as completion.
